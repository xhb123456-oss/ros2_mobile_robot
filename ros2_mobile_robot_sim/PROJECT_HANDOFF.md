# 项目交付与面试准备

## 现在做什么

当前技术验证阶段结束。先保存可恢复源码，再录一段演示，最后准备讲解。
不需要为了视频再次运行 20 段长测；演示运行也不自动算入已记录的 24 段验收。

### 1. 保存成果（用户仍需执行）

Windows 共享项目路径为 `/mnt/hgfs/robot_project`。Ubuntu 中另存有两个修复工作区，
只保存 Windows 项目是不完整的。至少保存：

- `~/ros2_ws/src/ros2_mobile_robot_sim` 和 `~/ros2_ws/maps`；
- `~/tf2_fix_ws/src` 和 `~/nav2_goal_fix_ws/src`（包含实际修改，不只是原版压缩包）；
- Windows 共享项目中的 launch、config、scripts 和说明文档；
- `AMCL_UPDATE_TRIAL.md` 列出的三组结果、控制台日志和原始 bag，保留以前失败样本供分析。

源码备份不包含 build/install，也不等于重建验证完成。请另行保留现有虚拟机或其备份，
以及编译所需版本记录。原始 bag 较大，单独保留，不必全部上传 GitHub。
当前 Windows 项目目录没有 `.git` 信息，尚未核对或更新简历中的远程仓库。

### 2. 录制 2～3 分钟演示（用户仍需执行）

用现有通过验证的组合，展示一轮 B→A。视频应包含：

1. 开头约 10 秒：说明“ROS 2/Nav2 固定地图自主导航仿真”。
2. Gazebo 与 RViz 并排显示，让观众看到实体模型、障碍物、激光和规划路径。
3. 起点位于 A 附近，运行已记录的 `--rounds 1 --finish-diagnostics` 命令，
   显式传入 `--behavior-tree /mnt/hgfs/robot_project/config/replanning_02hz_trial.xml`。
4. 展示绕障、到 B 后返回 A，末尾保留 SUMMARY 与停车误差。
5. 最后一页注明历史验收 24/24 来自三组测试，不是由视频单次运行证明。

只在上一导航任务已完成、没有遥控或其他导航命令时运行。若新演示出现失败，保留日志，
不要把失败裁剪后描述为完整成功。共享或公开视频前检查个人信息。

### 3. 面试讲解提纲（应能脱离文档回答）

用 90 秒说明：做了什么、遇到什么问题、如何查证、最终结果及范围。

- 系统：模型与驱动、scan/odom/TF、AMCL、全局规划、DWB 和行为树如何连接。
- 到点误差：为什么 SUCCEEDED 不代表停车后一定满足验收？为什么同时观察 map、odom 和 AMCL？
- 一个具体失败：旧阈值重启后第一段 7.23→16.03 cm；同一时间段 odom 位移约 0.164 cm，
  map 位移约 8.96 cm，支持定位修正为主要原因，而不是实际滑行这么远。
- 时间戳：旧路径创建时刻的目标变换与当前机器人位姿比较会有什么问题？
  阅读 `scripts/patch_goal_check_time.py` 并用自己的话解释修改，不能只背“修复 TF”。
- 规划：邻近快照上 Dijkstra 有有效势场但提取失败，A* 提取成功；快照不是精确内部状态，
  算法更换也不保证所有路径都成功。
- 验证：区分 action 成功、外部 PASS、恢复次数、告警和无有效轨迹；说明 24/24 的样本范围。
- 限制：固定路线、静态环境、仿真 world odom、有限次数测试；没有独立真值精度验证。

本人负责与 AI 协助的内容应如实说明。没有读懂的源码修改，先补理解再作为个人核心贡献讲述。
不要把官方 Nav2 算法称为自研；不要声称自研 SLAM、PID 或真实硬件闭环，除非有对应实现证据。
